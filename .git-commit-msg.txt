feat: real Google Drive submission uploads (direct-to-Drive, OAuth)

Replaces the fully-stubbed upload-submission-file (mock file IDs, never
actually called the Drive API despite the "PRODUCTION" branch existing) and
sync-submission-to-gdrive (callGoogleDriveMCP just logged and returned
{success:true}, had hardcoded test folder ID and a leftover test email
from earlier debugging) with a real implementation.

Architecture change, not just added credentials: the old flow read the
whole file as base64 in the browser and POSTed it as one JSON body to an
Edge Function - this cannot work for real video submissions (Edge Function
body limits, ~33% base64 bloat, loading the whole file into a JS string).
Now:
  1. browser asks upload-submission-file to open a Drive resumable upload
     session for team_id/stage_id (Edge Function finds-or-creates the
     Team -> Stage folder structure, authenticates to Drive)
  2. browser PUTs the raw file directly to the Google-provided session URL -
     the file never passes through Supabase
  3. Drive's response (requested via fields=) already carries
     id/webViewLink/thumbnailLink, so no second authenticated call is needed

Auth: Google Service Accounts have no Drive storage quota of their own and
can't create files outside a Shared Drive (Workspace-only). Rather than
require a paid Workspace plan, this authenticates as a real Google account
via OAuth refresh token (GOOGLE_OAUTH_CLIENT_ID/SECRET/REFRESH_TOKEN),
uploading into that account's own Drive quota under the shared root folder.

No new database table: uploaded_submission_files (referenced by both old
functions) was never migrated into this database - the real, working
persistence path is submissions.payload (jsonb), already correctly handled
by src/lib/lab.ts saveSubmission. The Edge Function only prepares the Drive
session; it does not write to the database.

New: supabase/functions/_shared/google-drive.ts - shared Drive v3 client
(token refresh, find-or-create folder, open resumable session).
